# Bounded autonomy

The user reviews the first exact contract. This skill is active only when its `autonomy` is `within_contract`; selecting a skill or suggesting autonomy does not activate the mode.

1. Use the accepted outcome, owned paths, checks, limits and decisions as the working boundary. Choose routine reversible implementation details from repository evidence and continue through approved checks and repairs.
2. Record consequential choices and evidence with `execution-evidence`. Keep blockers specific: what is missing, why it matters and what would unblock progress.
3. Try reasonable alternatives within scope when a tool or implementation attempt fails. Stop within the existing retry/time/model budgets; waiting does not grant more authority.
4. Return for direction when a product decision is unresolved or the needed change alters scope, interfaces promised to users, protected expectations, permissions or budgets. Do not quietly substitute a smaller outcome.
5. Respect pause, cancellation and steering. A new task does not inherit this task's autonomy.

Output: completed authorized work with a reviewable decision trail, or a concrete amendment/capability request. Reversibility alone does not authorize unrelated cleanup, publication, deployment, purchases or messages to others. Ordinary approved execution already permits routine progress; this option makes the user's preference for unattended decisions explicit.

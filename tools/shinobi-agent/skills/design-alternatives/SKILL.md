# Design alternatives

Use when several approaches remain plausible and choosing poorly would create meaningful cost. State the decision and non-negotiable requirements before producing alternatives.

1. Develop a small set of genuinely distinct designs, not cosmetic variations. Give each its data/interface shape, ownership, failure behavior and integration implications.
2. Evaluate each against the same criteria: acceptance, compatibility, complexity, verification, operational burden and reversibility as relevant.
3. Seek evidence against the favored option. Prototype or benchmark only within an approved experiment; otherwise distinguish source reasoning from measured results.
4. Recommend a design with decisive tradeoffs and conditions that would change the recommendation. Do not average incompatible architectures into an unexplained hybrid.
5. Record the accepted choice and implications for the specification and tasks. Material decisions unresolved by existing authority return to the user.

Output: comparable designs, evidence, recommendation and unresolved questions. Additional independent reviewers may be useful but require available runtime support and approved budgets; this skill does not itself spawn them.
